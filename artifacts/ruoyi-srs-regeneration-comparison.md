# RuoYi 用户管理 SRS 再生成对比结论

## 1. 对比对象

- 验收基准：`docs/ruoyi-user-management-srs-v2.pdf`
- 基准拆解：`artifacts/ruoyi-srs-v2-baseline-analysis.md`
- 源码逆向草稿：`artifacts/ruoyi-user-management-srs-regenerated-draft.md`

---

## 2. 覆盖结论

第一版源码逆向草稿已经覆盖既有 SRS v2 的主要功能、字段、异常、权限和验收项。

已覆盖：

- FR-USER-001 到 FR-USER-012
- 用户账号、用户昵称、密码、手机号、邮箱、部门、岗位、账号状态、性别、备注、头像
- 用户账号唯一性、手机号唯一性、邮箱唯一性
- 初始密码为空
- 导入数据为空
- 角色关联和岗位关联清理
- 下级部门查询
- Error Handling and Messages
- Acceptance Criteria
- Boundaries and Exclusions

---

## 3. 主要差异

### 3.1 草稿更偏源码实现说明

草稿中加入了较多源码层细节，例如：

- access token
- 具体权限标识，如 `system:user:query`
- 具体配置键，如 `system.user.init-password`
- 具体接口语义，如按 `roleId` 查询

这些信息来自源码，适合追溯，但与既有 SRS v2 的业务化表达相比略偏实现层。

### 3.2 既有 SRS v2 更偏需求文档表达

既有 SRS v2 的表达更像面向需求分析、测试设计和 RAG 检索的正式需求文档，特点是：

- 章节结构清晰
- 业务规则集中表达
- 字段规则集中成表
- 异常处理集中成表
- 边界范围明确
- 技术实现细节较少

### 3.3 需要做的对齐动作

后续对齐稿应保留源码校验出的事实，但降低实现细节暴露程度：

- 将 `access token` 改写为“登录凭证”
- 将权限标识改写为“查看/新增/修改/删除/重置密码/导入/导出权限”
- 将配置键改写为“系统配置中的账号初始密码”
- 将 roleId 改写为“用户角色筛选”
- 保留字段、异常、业务规则和验收标准

---

## 4. 对齐策略

下一版对齐稿应采用以下原则：

1. 章节结构完全跟随既有 SRS v2。
2. 功能范围跟随源码逆向结果。
3. 表达风格向既有 SRS v2 靠拢。
4. 技术细节只保留对需求有解释价值的内容。
5. 不在正文中展示源码路径、接口路径或权限标识。
6. 保留连续段落，避免过度碎片化。

---

## 5. 当前结论

第一版源码逆向草稿已经证明：可以从 RuoYi-Vue-Pro 用户管理源码中抽取出与既有 SRS v2 基本一致的需求内容。

下一步应生成一版“对齐版 SRS”，作为后续 PDF 生成和 RAGFlow 分块验证输入。
