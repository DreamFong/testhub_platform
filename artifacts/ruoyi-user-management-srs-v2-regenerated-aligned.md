## 1 Introduction

### 1.1 Purpose

本文档定义 RuoYi-Vue-Pro 管理后台中用户管理模块的软件需求。文档目标是为需求分析、测试用例设计、接口验证和验收评审提供统一依据，并确保 RAG 知识库能够基于连续段落和清晰章节边界进行稳定解析。

### 1.2 Scope

本模块用于支撑后台账号的创建、维护、查询、禁用、删除、导入和导出。模块与部门、岗位、角色权限、租户账号配额、登录凭证、操作审计和组织协作存在业务关联，但不负责角色、部门、岗位、菜单权限、第三方登录、OAuth2 授权或前台会员用户本身的维护。

### 1.3 Definitions

| 术语 | 定义 |
|------|------|
| 后台用户 | 可以登录管理后台并使用后台功能的系统操作者。 |
| 用户账号 | 用户登录后台系统时使用的唯一账号。 |
| 用户昵称 | 用户在列表、详情和其他业务场景中的展示名称。 |
| 部门 | 用户所属的组织节点，支持按部门及下级部门筛选。 |
| 岗位 | 用户承担的岗位职责，一个用户可以关联多个岗位。 |
| 角色 | 用户拥有的权限集合，决定可访问菜单、按钮和数据范围。 |
| 账号状态 | 用户账号是否允许正常登录和使用系统。 |
| 初始密码 | 用户导入时由系统配置提供的默认密码。 |

## 2 Overall Description

### 2.1 User Classes

系统主要面向超级管理员、系统管理员、普通运维人员以及审计或只读人员。超级管理员拥有用户管理的全部操作能力；系统管理员根据授权维护用户账号；普通运维人员可在授权范围内查看和执行部分维护操作；审计或只读人员只能查看用户列表、用户详情和账号状态，不允许修改用户信息。

### 2.2 Product Perspective

管理后台需要对系统操作者进行统一维护。用户管理模块是后台权限体系的基础能力之一，用户资料会被角色授权、数据权限、部门筛选、岗位维护、登录凭证和审计记录等能力引用。因此，用户管理模块必须保证账号数据准确、状态可靠、权限校验一致，并支持管理员在高频运维场景下快速完成查询和维护。

### 2.3 Business Process Overview

用户维护的一般流程是管理员进入用户管理页面，系统展示部门树、查询区和用户列表，管理员根据需要新增、编辑、删除、查询、重置密码、修改状态、导入或导出用户。系统对管理员输入进行合法性校验，校验通过后保存用户信息，并刷新用户列表展示最新数据。

新增用户时，管理员必须填写用户账号、用户昵称和密码，并可填写手机号、邮箱、部门、岗位、性别、头像和备注等信息。系统校验必填项、格式、长度、唯一性、部门岗位有效性以及租户账号数量限制。校验通过后系统创建用户，账号状态默认为正常。

用户导入流程由模板下载、数据填写、文件上传、数据校验和结果反馈组成。系统使用配置中的账号初始密码作为导入用户的默认密码；如果初始密码为空，系统应阻止导入并提示初始密码不能为空。导出流程则根据当前查询条件生成用户数据文件。

## 3 System Features

### 3.1 User Management Functional Requirements

#### 3.1.1 用户列表查询

FR-USER-001 系统应默认展示后台用户列表，并支持按用户账号、手机号码、账号状态、创建时间范围、所属部门和用户角色进行筛选。按部门筛选时，结果应包含所选部门及其下级部门的用户。按角色筛选时，结果应限定为拥有该角色的用户。查询结果应分页展示；当没有匹配数据时，系统应展示空数据提示或返回空分页结果。

#### 3.1.2 获取启用用户精简列表

FR-USER-002 系统应提供启用用户精简列表，用于分配用户、选择负责人、选择审批人等下拉场景。该列表只返回账号状态为正常的用户，并包含必要的展示信息。

#### 3.1.3 查看用户详情

FR-USER-003 管理员应能够查看单个用户的详细信息。详情信息应包含用户基础资料、所属部门、岗位、账号状态、创建时间和最后登录信息；当用户不存在或已被删除时，系统应返回空结果。

#### 3.1.4 新增用户

FR-USER-004 管理员应能够新增后台用户。新增用户的必填字段包括用户账号、用户昵称和密码；可选字段包括所属部门、岗位、手机号、邮箱、性别、备注和头像。新增用户时不能选择账号状态，系统应默认创建为正常状态。

FR-USER-005 创建用户时，系统应校验当前租户账号数量、用户账号唯一性、手机号唯一性、邮箱唯一性，以及部门和岗位是否可用。用户账号重复时，系统应阻止创建并提示账号已存在；手机号重复时提示手机号已存在；邮箱重复时提示邮箱已存在。创建成功后，新用户应出现在用户列表中，并可被后续角色授权功能选择。

#### 3.1.5 编辑用户

FR-USER-006 管理员应能够编辑已有用户资料。可编辑内容包括用户账号、用户昵称、手机号、邮箱、部门、岗位、性别、头像和备注。普通编辑入口不应修改密码和账号状态；保存成功后，用户列表和详情应展示最新信息。

#### 3.1.6 删除用户

FR-USER-007 管理员应能够删除单个用户或批量删除多个用户。删除前系统应提示确认；删除成功后，系统应同时清理用户角色关联和岗位关联数据，被删除用户不应继续出现在用户列表中，也不应继续登录后台系统。删除不存在的用户时，系统应给出失败提示。

#### 3.1.7 重置密码

FR-USER-008 管理员应能够为用户重置密码。新密码必须符合系统密码规则；密码重置成功后，用户应使用新密码登录，且密码重置不应改变用户其他资料。密码格式不符合要求时，系统应提示密码规则。

#### 3.1.8 修改账号状态

FR-USER-009 管理员应能够将正常用户停用，也应能够将停用用户恢复为正常。停用用户不允许登录后台系统；已登录用户被停用后，不应继续使用后台功能。账号状态变更不应改变用户基础资料。

#### 3.1.9 用户导入

FR-USER-010 系统应提供用户导入模板下载，并支持管理员按照模板导入新用户。导入模板应包含登录名称、用户名称、部门编号、用户邮箱、手机号码、用户性别和账号状态等字段。导入时系统应使用配置中的账号初始密码作为默认密码；如果该密码配置为空，导入应失败，并提示初始密码不能为空。

FR-USER-011 系统应支持在管理员选择允许更新时更新已存在用户。导入过程中，系统应对文件内容、必填项、格式、唯一性和关联数据进行逐条校验，并在导入完成后展示成功和失败结果，失败结果应说明失败原因。导入文件为空或无有效数据时，应提示导入数据不能为空。

#### 3.1.10 用户导出

FR-USER-012 管理员应能够导出当前查询条件下的用户数据。导出内容应包含用户列表中的主要字段；当没有符合条件的数据时，系统应允许导出空结果或提示无可导出数据。

### 3.2 Page and Interaction Requirements

用户管理页面应由部门树、查询区、操作区、用户列表和分页区组成。页面左侧展示部门树，部门树应体现上下级部门关系，并支持展开和收起。管理员选择某个部门后，用户列表应展示该部门及其下级部门的用户。

查询区应支持用户账号、手机号码、账号状态、创建时间范围、所属部门和用户角色等筛选条件，并提供重置能力。操作区应根据当前登录用户权限展示新增、删除、批量删除、导入、导出、下载导入模板和重置密码等按钮。用户列表应展示用户编号、用户账号、用户昵称、所属部门、手机号、邮箱、性别、账号状态、最后登录信息、创建时间和操作按钮，并支持分页展示。

新增或编辑用户时，页面应展示用户账号、用户昵称、部门、岗位、手机号、邮箱、性别、头像和备注等表单项。新增用户必须填写密码；编辑用户时普通编辑入口不提供密码修改和状态修改能力。删除、批量删除等高影响操作应提供确认机制。

### 3.3 Data Requirements

| 字段 | 必填 | 规则和说明 |
|------|------|------------|
| 用户账号 | 是 | 新增用户必填，用于登录后台系统，在系统内必须唯一，只能包含字母和数字，长度为 4 到 30 个字符。 |
| 用户昵称 | 是 | 新增用户必填，用于列表、详情和其他业务场景中的用户展示，长度不超过 30 个字符。 |
| 密码 | 新增/重置必填 | 新增用户和重置密码时必填，长度为 4 到 16 位，不应在列表或详情中明文展示。 |
| 手机号码 | 否 | 如果填写，必须符合手机号格式，并且应在系统内唯一。 |
| 邮箱 | 否 | 如果填写，必须符合邮箱格式，长度不超过 50 个字符，并且应在系统内唯一。 |
| 部门 | 否 | 如果选择部门，只能选择可用部门；用户列表支持按部门筛选。 |
| 岗位 | 否 | 可选择一个或多个岗位；如果选择岗位，只能选择可用岗位。 |
| 性别 | 否 | 使用系统性别字典值。 |
| 备注 | 否 | 用户补充说明。 |
| 头像 | 否 | 用户头像地址。 |
| 账号状态 | 系统控制 | 新增用户默认为正常；状态修改通过独立启用或停用功能完成。 |

### 3.4 Business Rules

用户账号必须唯一，手机号和邮箱在填写后也必须唯一。用户账号保存后应作为用户登录标识，用户密码不得明文展示。

新增用户时账号状态默认为正常，不支持选择初始状态。创建用户前，系统应校验当前租户账号数量是否已达上限，达到上限后禁止创建。

停用用户不能登录后台系统。被停用的已登录用户，系统会删除其登录凭证，不应继续访问后台功能。删除用户时，系统应同时清理该用户的角色关联和岗位关联数据。

新增或编辑用户时，选择的部门和岗位必须可用。查询部门用户时，应包含所选部门及其下级部门。导入用户时，系统应逐条校验并返回成功和失败结果。

### 3.5 Permission Requirements

| 权限场景 | 规则 |
|----------|------|
| 访问控制 | 未登录用户不能访问用户管理页面；无查看权限的用户不能访问用户列表和用户详情。 |
| 新增/编辑/删除 | 无对应权限的用户不能新增、修改用户资料、修改账号状态或删除用户。 |
| 密码/导入/导出 | 无重置密码、导入或导出权限的用户不能执行对应操作。 |
| 前后端一致性 | 页面按钮应根据当前登录用户权限动态展示，后端也必须进行权限校验。 |

### 3.6 Error Handling and Messages

系统应在用户输入、关联基础数据、导入文件和权限校验失败时给出明确提示。错误提示应面向管理员可理解，避免泄露系统内部异常信息。

| 异常场景 | 系统处理 |
|----------|----------|
| 用户账号重复 | 系统应阻止创建或保存，并提示账号已存在。 |
| 手机号码重复 | 系统应阻止创建或保存，并提示手机号已存在。 |
| 邮箱重复 | 系统应阻止创建或保存，并提示邮箱已存在。 |
| 用户不存在 | 查看详情返回空结果；编辑、删除、重置密码或修改状态时应提示用户不存在。 |
| 部门或岗位不可用 | 系统应提示所选部门不可用或所选岗位不可用。 |
| 密码格式不符合规则 | 系统应阻止提交，并提示密码规则。 |
| 导入文件为空或无有效数据 | 系统应提示导入数据不能为空。 |
| 导入初始密码为空 | 系统应阻止导入，并提示初始密码不能为空。 |
| 导入部分失败 | 系统应展示失败明细，便于管理员修正后重新导入。 |
| 超过租户账号配额 | 系统应阻止创建用户，并提示超过租户账号配额。 |

## 4 Non-functional Requirements

### 4.1 Security

用户管理操作必须受登录态和权限控制保护。密码不得明文存储或明文展示。停用用户时，系统会删除该用户的登录凭证；删除用户时，系统会清理用户角色关联和岗位关联数据；导入文件应进行格式和内容校验。

### 4.2 Usability

查询、重置、导入、导出、新增、编辑和删除等操作应提供明确的成功或失败反馈。表单校验应尽量在提交前提示，批量操作应提供确认机制以避免误操作。页面展示文案和错误提示应清晰一致。

### 4.3 Performance and Maintainability

用户列表应分页加载，查询条件变化后应及时刷新结果。导出大量数据时应避免影响正常页面操作。用户字段、状态、性别等基础数据应保持统一口径，导入模板字段应与新增用户表单保持一致。

## 5 Acceptance Criteria

| 验收项 | 验收标准 |
|--------|----------|
| 用户列表 | 管理员进入用户管理页面后可以看到用户列表；可以通过账号、手机号、状态、创建时间、部门和角色筛选用户；查询无结果时页面展示空数据提示。 |
| 新增用户 | 管理员填写用户账号、用户昵称和密码后可以成功创建用户；创建的用户状态默认为正常；账号、手机号或邮箱重复以及字段格式不合法时，系统阻止提交并提示原因。 |
| 编辑用户 | 管理员可以修改用户基础资料；修改成功后，用户列表和详情展示最新数据；普通编辑入口不提供密码修改和状态修改能力。 |
| 删除用户 | 删除前系统展示确认提示；确认后用户被删除并从列表中移除；删除时系统同时清理用户角色关联和岗位关联数据。 |
| 重置密码 | 管理员输入合法新密码后可以成功重置密码；新密码不符合规则时系统阻止提交并提示原因。 |
| 修改状态 | 管理员可以停用或启用用户；停用后用户不能继续登录或使用后台功能。 |
| 导入导出 | 管理员可以下载导入模板并导入合法数据；导入错误时展示失败明细；管理员可以导出当前查询条件下的用户数据。 |

## 6 Boundaries and Exclusions

用户管理只维护后台系统用户，不维护前台会员用户。用户角色分配属于权限管理能力，不在本模块内展开。部门和岗位的新增、编辑、删除由对应管理模块负责。菜单和按钮权限配置由菜单管理和角色管理模块负责。第三方登录、OAuth2 授权、社交账号绑定和前台会员用户管理不属于本模块范围。
