# 风险登记表

## 目标

记录 SRS Skill 化实施过程中的主要风险、触发信号和缓解措施。

## 风险 1：Scope 自动推断过宽

触发信号：

- 候选范围包含大量跨模块能力
- SRS 章节明显膨胀
- 用户确认时需要排除大量项目

缓解措施：

- 强化相邻能力识别
- 把跨模块依赖默认放入“待确认”
- 未确认不进入正式生成

## 风险 2：Scope 自动推断过窄

触发信号：

- 漏掉导入导出、批量操作、状态变更等边界功能
- 独立评审指出核心功能缺失

缓解措施：

- 增加权限码、错误码、DTO 搜索信号
- 在确认问题中显式询问是否有遗漏项

## 风险 3：SRS 变成源码说明文档

触发信号：

- 章节大量描述类名和方法名
- 缺少用户视角的功能需求
- 验收标准不完整

缓解措施：

- 保留事实草稿与正式 SRS 两阶段
- 在改写 prompt 中强调需求文档表达
- 在评分中保留“需求表达质量”维度

## 风险 4：生成内容编造

触发信号：

- SRS 中出现 evidence map 无法支撑的规则
- reference_srs 内容覆盖了源码事实
- domain_hints 被写成确定需求

缓解措施：

- 强制 source_evidence_map
- 无依据关键结论触发 fail 或人工复核
- 明确参考件只用于风格，不作为事实来源

## 风险 5：PDF 不适合知识库解析

触发信号：

- PDF 文本层不可提取
- 中文乱码
- FR 编号无法检索
- 表格内容丢失或错乱

缓解措施：

- 默认 kb-friendly 连续段落
- 控制表格使用
- 在 Skill A 内执行文本层检查

## 风险 6：Skill A 过拟合用户管理案例

触发信号：

- 第二样本 scope 推断失败
- 第二样本文档结构不自然
- Prompt 中出现用户管理专有假设

缓解措施：

- 增加第二样本验证
- 抽象功能类型而非具体业务名称
- 根据验证结果修订 prompt

## 风险 7：Skill B 过早复杂化

触发信号：

- 尚未稳定 sanity check 就引入 RAGAS
- 知识库指标复杂但不可解释

缓解措施：

- 先使用固定检索问题集
- 后续再引入 RAGAS
- 保持 retrieval gate 可人工解释

## 风险 8：执行约束污染纯 SRS 知识库

触发信号：

- token、userId 提取规则被混入纯需求 SRS
- 知识库职责不清

缓解措施：

- Skill A/B 维护纯 SRS 链路
- Skill C 单独维护执行约束
- 总编排中清晰区分需求知识和执行增强
